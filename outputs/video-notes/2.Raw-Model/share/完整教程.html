前置知识 · 从 Agent 应用到裸模型

前置知识 / 建立全局视角

使用 AI 时，你看到的往往是一个聊天窗口或编程助手；应用背后调用模型服务，服务再组织底层模型的推理。先把这三层分开，就能理解：为什么裸模型只计算下一个 Token 的概率，整个应用却能与人对话、读取文件和完成任务。

同一次任务，三层分别负责什么？
层次接收什么主要处理交出什么
AI 应用用户目标、已有对话和可用资源组织提示与上下文，调用服务，处理回复；需要时协调工具执行给服务的请求，以及给用户的结果或实际操作
模型服务符合接口格式的消息与配置输入编码、推理调度、逐步生成及输出解码；还可提供鉴权等服务功能文本或结构化调用信息等接口响应
裸模型编码后的序列及必要的模型输入用模型架构和已训练权重完成计算用于选择下一 Token 的分数／概率分布

Agent 放在哪里？本课把 Agent 放在应用层理解：应用可以依据模型的输出调用工具、查看结果，再继续请求模型。AI 应用的范围更广，一个只做单次文本改写的应用，也可以调用模型服务，但不必具有这样的 Agent 循环。

这是一张职责图，不是固定部署图。应用和服务不一定是独立程序，也可能共同承担工具、上下文等功能。本文讨论的是课程中的自回归语言模型；“输入 Token → 下一 Token 的概率”是帮助理解这类模型生成过程的简化视角，不代表所有 AI 系统都采用同一种结构。

接下来把视线收回最底层：暂时放下聊天界面、接口和工具，先看 Raw Model 接收什么、计算什么，再逐步接回上层能力。

01 · 剥离上层功能，先看 Raw Model

好，各位同学，咱们今天聊的是 Raw Model，这节课把它叫作“裸模型”。什么意思？就是先把聊天界面、模型服务和工具调用这些上层功能放到一边，看看底下的模型本身在做什么。

这里先限定一下：咱们主要讲的是用来生成文本的自回归语言模型。后面说的“输入 Token，预测下一个 Token”，都是围绕这类模型展开，不是说所有 AI 都只有这一种工作方式。

有些资料还会提到“基础模型”，英文叫 Foundation Model。它强调的是模型经过广泛数据的训练，可以适配多种任务，跟这里为了讲课方便使用的“裸模型”不是严格相同的概念。咱们先记住这节课的意思：把上层封装拿开，看模型的输入、计算和输出。

从 2022 年底 ChatGPT 发布以来，大家越来越熟悉这种对话方式。模型的能力、架构和训练方法一直在发展，但对于这里讨论的模型，“根据已有内容预测下一个 Token”仍然是理解文本生成的一条重要线索。

那这个模型到底怎么理解呢？先把它看成一个带参数的函数：接收输入，经过计算，产生输出。对于文本输入，可以先把 Token 列表理解成一个数字数组，后面再来看这些数字怎么来的。

02 · 自然语言如何变成 Token 列表

比方说，这里有一串数字：2、3、4、5、1、8。它们只是课堂示意，实际编号要看具体分词器。文本会被拆成一个个 Token，再映射成相应的编号，形成模型处理的输入。

那么，一个中文字对应几个 Token？没有一个对所有模型都适用的固定答案，要看模型使用的分词器，也要看具体文字。

有时候，一个 Token 可以表示一段文字；有时候，一个字又需要拆成多个 Token。英文也是一样，一个单词可能整体编码，也可能被拆成几部分。所以不能把“一个 Token”直接当成“一个字”或者“一个单词”。

为了方便后面估算，咱们暂时假设中文平均一个字占 1.5 个 Token，英文平均一个单词占 1.3 个 Token。注意，这是本课算例采用的假设，不是通用换算公式。实际使用时，要用对应模型的分词器来数。

画面与校读说明

便笺中的数字数组只是示意。中文 1 字约 1.5 Token、英文 1 单词约 1.3 Token 是本课算例的假设，不是通用比例；实际数量取决于分词器与文本。

03 · 输出是下一个 Token 的概率分布

把这串 Token 传给模型，得到的是什么？从理解上讲，是下一个 Token 的概率分布。

更准确一点，很多实现会先得到一组分数，叫作 logits，再通过 softmax 把这些分数转换成概率。你暂时不用去推导这个公式，只要分清两件事：模型先算出各个候选的分数，再由生成程序按照相应策略选择下一个 Token。（是把一组分数转换成概率的函数，转换后的概率总和为 100%）

比如，某个候选 Token 的概率是 0.7，另一个是 0.2。这是在说哪些候选更有可能，还没有等于最终选中了哪一个。这里的数字只是教学示意，不是某个模型实际测出来的结果。

这些编号和文本之间有对应关系，所以生成的 Token 序列可以解码成自然语言。比如已有内容是“你好”，后面可能接逗号，也可能接“吗”。这只是帮助理解续写的例子，不表示这里的每个字都一定对应一个 Token。

补充理解 / 从预测到生成

一个概率分布，如何变成完整回答？

原课这一节讲的是模型的一次预测。完整回答需要生成程序反复使用这种能力：每选出一个新 Token，就把它接到已有序列后面，作为下一步预测的依据。在这里，我们将这段生成逻辑放在模型服务层理解；本地推理库也可以承担它。

读得见的例子：问题“你是谁？” → 选出“我” → 根据问题和“我”继续预测 → 选出“是” → 根据问题和“我是”继续预测 → …… → 停止。这里用文字片段帮助理解，一个字或一个词并不保证恰好对应一个 Token，也不是某个模型的实测输出。

选出一个 Token 之后，把它接到已有序列后面，再继续预测下一个。满足结束条件，就停止生成。那是不是非得等全部生成完，才能看到回答？不一定。可以生成完再统一返回，也可以边生成、边解码、边把文字传回来。咱们平时看到回答一点点出现，就是流式返回的一种常见效果。

模型给出候选分布，采样则根据配置从候选中选择 Token。temperature、top_k、top_p 等用于调节采样，但服务支持哪些选项、怎样组合，要看具体接口。它们不等于重新训练权重，也不能简单理解成“设一个值就保证正确或完全可复现”。

04 · 上下文窗口：长度与容量估算

补充理解 / 看清输入的组成

上下文里到底装了什么？

模型拿到的输入，通常不只是聊天框里刚输入的那句话。应用与服务会组织本次需要的内容，再按模型要求的消息模板、角色标记和编码方式准备输入；具体格式随服务与模型而变化。

长度与容量要分开。当前输入长度是这次实际送入多少 Token；上下文容量是模型或服务支持处理的上限。在本课讨论的生成流程中，输入和新生成内容共同占用序列空间。接口还可能单独限制输入或输出，因此应结合具体接口计算可用预算。

容量与超限处理：服务可能拒绝超限请求，或按配置截断；应用也可能先筛选、压缩历史，再提交输入。不能依赖裸模型统一自动截断。下面的中文字符换算只用于演示计算方法，实际 Token 数应以对应分词器为准。

持续对话通常是在改变这次提供的上下文，不等于实时训练或修改模型权重。普通推理使用已有权重；训练和微调是另外的过程，后文第 7 节会继续说明。

第一个概念，叫作上下文窗口，Context Window。这里有两个东西要分清：这次实际输入了多少 Token，以及模型或者服务最多允许处理多少 Token。

比如这次传入的列表有 100 个 Token，说明当前输入长度是 100，不能因此就说这个模型的上下文窗口只有 100。模型支持的上下文容量，说的是它能处理的上限。

对于咱们这里讨论的生成过程，已有输入和后面新生成的内容，都需要占用相应的序列空间。具体能输入多少、最多输出多少，还要看服务接口的限制，不能只盯着一个标称容量。

超过限制会怎么样？也不能一概而论。有的接口会直接报错，有的会按照配置截断，有的应用会先压缩或者筛选历史，再把内容发出去。不是说裸模型一定会自动把开头扔掉。

再看容量估算。咱们这个例子把 128K 按 128,000 个 Token 来算，再假设平均每个中文字占 1.5 个 Token，那么就是大约 8.5 万个中文字。按同样假设，1,000,000 个 Token 大约对应 66.7 万个中文字。这个算式没有问题，但前提要记住：实际容量和实际分词结果，要以具体模型及接口为准。

这里的 K、M 用来描述 Token 的数量，不是磁盘空间。算出一个大概能装多少内容的数字，也不代表模型一定能把这些内容都处理好，下一节继续说这个区别。

画面列出上下文容量与 Token 数量。请区分当前输入长度和容量上限；实际输入、输出预算及超限处理由具体接口决定，不能依赖统一的自动截断行为。字符换算仅使用本课声明的估算假设。

05 · 装得下，不代表处理得好

装得下，是不是就一定处理得好？不是一回事。

同学们可能有过这种体验：对话越来越长，先前约定的一些规则没有被遵守。为什么会这样？可能是模型没能有效利用长上下文里的信息，也可能是应用已经截断、压缩了历史，或者前后出现了相互冲突的要求。不能只看到“忘了”，就认定是某一种原因。

所以，相对独立的任务可以考虑新开对话，让输入更集中。不过新开对话之后，必要的背景和规则也要重新提供，不能既把上下文清掉，又指望它保留原来的所有信息。

有些应用还会用子代理，把子任务放到相对独立的上下文里处理。这是一种组织任务的办法，但能不能改善效果，还取决于任务怎么拆、信息怎么传，不是用了子代理就一定更好。

接下来再回到模型这个方框。前面把它看成一个函数，没有问题。现在我们进一步看看：这个函数做计算时，会用到什么？会用到模型架构规定的计算过程，以及训练得到的一组参数，也就是接下来要讲的权重。

板书由输入序列的容量转向模型计算。长对话表现可能同时受模型利用信息的能力、应用保留的历史和指令冲突影响；图中的模型方框仍可以理解为带参数的计算函数。

06 · 权重矩阵、下载体积与参数量

有些同学在本地部署过模型，会先下载一批文件。里面很重要的一部分，就是模型的权重。

权重是什么？可以先理解成大量参与计算的数字。更准确地说，它们通常分布在许多参数张量里，有的像矩阵，有的像向量，不是整个模型只有一张大矩阵。下载包里还可能有模型配置、分词器等文件，这些也要配合起来使用。

平时说一个模型有多少参数，主要是在说这组参数里有多少个标量。比如 7B，B 是 billion，也就是十亿，7B 就是七十亿。这里数的是参数个数，不是文件有多少字节。T 是 trillion，也就是万亿，同样表示参数个数的量级。

参数量和下载体积有关，但不是同一个东西。同样数量的参数，用不同精度存储，占用的空间就可能不同。所以看到一个模型文件有几个 G，不能直接把它当成有几个 B 的参数。

至于某个具体模型究竟有多少参数，要看可靠的公开资料。没有公布或者没有核实的数字，咱们就不拿来当例子。先把 B、T 这些单位和参数量的含义理解清楚，就够了。

画面与校读说明

画面中的“权重矩阵”是简化称呼，实际模型通常包含许多参数张量。7B 表示约七十亿个参数，参数个数不能直接当作文件字节数；具体模型规模以可靠公开资料为准。

07 · 训练、微调，以及语料为什么重要

训练是什么？不是一开始连参数都没有，训练完了才突然出现一组数字。

从头训练的时候，一般会先把模型结构搭好，再给参数设置初始值。接着拿训练数据来计算，看看结果与训练目标差在哪里，再通过优化过程一点点调整参数。这样反复进行，得到训练后的权重。

那微调呢？就是从一个已经预训练过的模型出发，继续用数据训练，让它更适合某类任务或者某种要求。

微调的做法也不只有一种。可以更新原模型的全部参数，也可以只更新一部分；还有像 LoRA 这样的方式，把原权重先固定住，另外训练一小组适配参数。你先不用深入算法，记住它们都在利用已有模型的基础，继续调整模型的行为。

对这里讨论的语言模型来说，训练数据非常重要，文字和代码都可以成为训练材料。但不是数据越多就一定越好，数据质量、覆盖范围和训练方法也会影响结果。编程模型的能力，开源代码数据提供了重要基础，也需要相应的训练和评估方法配合。

画面与校读说明

“训练/微调”箭头表示利用数据优化参数。从头训练先初始化参数；微调可以更新原参数，也可以冻结原权重、训练适配器。不是先没有参数，再由训练凭空生成参数。

08 · 通过模型架构调用权重

有了权重，是不是就可以直接用了？还不行。你给我一大堆数字，我还得知道这些数字应该放在哪些位置、按什么顺序参与计算，对吧？这就涉及模型架构。

Transformer 是一种模型架构。很多语言模型都采用它，或者采用它的变体。运行模型时，需要使用与权重相匹配的结构和配置，才能把计算正确地做出来。

这里有几个名字比较容易混：Transformer 是架构；Hugging Face 的 Transformers 是一个软件库，可以用来加载和运行它支持的模型；Tensor 则是“张量”，是表示数据和参数的一种形式，不是与 Transformer 并列的另一种架构。

也不是所有语言模型都采用 Transformer。即使都使用 Transformer，层数、维度和具体结构也可能不同，权重不能随便互换。至于模型转换，需要看两种实现是否兼容，不能理解成换个名字或者随便转换一下矩阵，就能放到另一种架构里运行。

画面与校读说明

画面中的“Tensor架构”用词不准确：Tensor 指张量，是数据结构，不是模型架构。Transformer 是架构，Transformers 是软件库，运行时还需与权重匹配的结构和配置。

09 · 输入、权重与算法共同产生输出

把前面的内容合起来看：输入提供这次要处理的信息，权重提供训练得到的参数，架构规定怎么计算。三者配合，得到下一步预测所需的分数或者概率分布。

在固定参数、固定计算规则的数学抽象下，可以把它写成一个函数。这个理解很有用，但它不等于说实际运行的整个聊天系统，每次都保证输出完全一样的文字。

一方面，生成程序可能采用随机采样；另一方面，实际计算还会受到数值精度、算法实现和运行环境等因素影响。所以咱们要区分数学上的计算关系，以及具体系统能不能逐位复现同一个结果。

画面与校读说明

图中的输入、架构与权重共同定义计算关系。固定参数与计算规则下的函数抽象，不等于实际服务对重复请求保证完全相同的输出。

10 · 数学函数、GPU 与浮点数误差

计算机里的浮点数精度是有限的，一些十进制小数不能被精确表示。这个问题不是 GPU 才有，普通 CPU 计算也会遇到。

比如在 JavaScript 里，0.1 + 0.2 + 0.3 会显示为 0.6000000000000001，而 0.1 + (0.2 + 0.3) 会显示为 0.6。显示成 0.6，也不代表计算机就精确存下了数学上的六分之十。

这个例子说明：改变运算的结合顺序，浮点结果可能发生变化。大规模并行计算中，如果计算顺序或实现方式不同，也可能出现数值差异。但不能反过来说，只要用了 GPU，每次运行就必然不同。

至于模型有没有理解、感情或者自我意识，这些问题不能仅凭“它进行了数学计算”就下结论。这节课先把计算过程讲清楚，不用这个函数示意去证明这些问题。

画面与校读说明

原课控制台两式比较为 false，示范的是有限精度浮点运算不满足结合律；显示 0.6 不代表精确表示了十进制的 0.6。这个问题不限于 GPU，也不能单凭它判断模型是否具有理解或意识。

11 · 多模态：数字输入与输出解释

前面一直拿文字举例，那图片、音频和视频怎么办？它们也需要变成模型能够处理的数字表示，但变成数字，不代表处理方式就完全一样。

文字可以通过分词器变成 Token；图像、音频等内容，则需要相应的编码和处理机制。具体怎么表示、怎样送进模型，要看模型的设计，不能把所有模态都理解成同一张文字字典。

输出的时候也是一样。生成文字，需要把相应的 Token 解码成文本；生成图像或者音频，则需要对应的生成和解码过程。比如图像生成可以采用扩散模型，就不是简单地查一个 Token 编号，再把它换成某个像素。

所以，多模态这一块先记住三个环节：不同内容先经过相应的编码，模型处理这些表示，最后再按目标模态生成或解码输出。具体内部结构，这节课先不展开。

画面与校读说明

画面里“多模态 没有区别”和按编号判断图像的示意过于简化，不能作为通用实现。不同模态采用相应的编码、处理与生成或解码机制；图像输出不一定通过文字式 Token 字典恢复像素。

12 · 回到整体结构，衔接模型服务

到这里，我们可以把前面的知识放回同一张图了：输入内容经过编码，模型结合已有权重进行计算，生成程序再利用预测结果，一步步组织输出。

对于这节课讨论的自回归语言模型，“根据已有序列预测下一个 Token”是一条贯穿全文的线索。但这不表示模型技术一直没有变化，也不表示不同模型只差一组权重和一个上下文长度。

模型架构、分词器、训练数据、训练目标以及支持的模态，都可能不同。这些差别会影响它能做什么、做得怎么样，以及运行时需要多少资源。

先把这一层理解清楚，再往上看就容易了：模型服务怎样组织输入和生成，AI 应用又怎样使用回复、执行工具、继续完成任务。前面的三层关系，到这里就接起来了。

画面与校读说明

整体图概括文本自回归生成：输入、架构与权重参与计算，输出供生成程序继续使用。图中的 GPU 是计算设备示例；训练与微调优化参数，模型之间也可能在架构、分词器和训练方法等方面不同。

综合案例 · Agent 如何读取技能并继续完成任务？

补充理解 / 把三层重新接起来

依据《AI 本质》第 17—18 节的技能调用案例整理。以下展示该课程的简化流程，不代表所有 Agent 产品都采用同一种技能机制或请求格式。

回到开篇的任务：“请按设计规范检查这个页面。”应用已经知道可用技能的名称和简要说明，但第一轮不一定会把完整技能文档都放进输入。当模型生成需要该技能的调用信息时，应用再读取文档，并把结果交给后续请求。

生成调用信息 ≠ 执行动作。这个案例由应用读取技能文档；其他产品也可能由服务侧的执行程序提供工具能力。无论放在哪层，都需要真实的执行程序把动作完成，再把结果接回后续流程。

两种循环，分别解决什么问题？
循环每一步在做什么什么触发继续得到什么
Token 生成循环预测、选择并追加下一 Token尚未达到结束标记或其他停止条件一次请求中的文本或调用信息
Agent 工具循环请求服务、执行工具、带着结果再次请求任务还需要工具反馈或后续步骤利用实际环境反馈推进任务的结果

遇到新概念，沿着输入与输出去看

  • ① 给模型增加了什么输入？是规则、历史、技能说明，还是刚得到的工具结果？
  • ② 返回结果由谁继续处理？是直接展示，还是由执行程序读取文件、调用工具，再请求模型？

这样再看三层关系就完整了：裸模型提供底层计算，服务组织可调用的生成能力，应用围绕用户目标把输入、输出与真实操作接起来。
