# 2.AI最底层的Raw Model - 图文解说

## 01. 剥离上层功能，先看 Raw Model（00:00-01:11）

![场景 1](<keyframes/scene_001_00-01-04.jpg>)

### 完整内容

Raw Model 在本教程中称为“裸模型”，位于 AI 技术体系的底层。上层技术最终都需要调用这一层的模型能力。

相关资料也会使用“基础模型”或“原始模型”等译法。“裸模型”这一名称强调暂时剥离上层功能，观察模型最基础的工作方式。

原课认为，从 2023 年 GPT-3.5 受到广泛关注至录制时，这一层的核心知识框架和调用方式相对稳定。

可以先将模型理解为一个函数：接收输入，产生输出。输入称为 Token 列表，可以将其想象成一个数字数组。

### 画面说明

白板中心是 Raw Model 方框，左侧箭头指向模型，右侧箭头从模型引出，建立输入与输出的函数示意。

## 02. 自然语言如何变成 Token 列表（01:11-02:05）

![场景 2](<keyframes/scene_002_00-01-52.jpg>)

### 完整内容

例如，Token 列表可以表示为 2、3、4、5、1、8，各数字也可能更大。Token 是自然语言经过分词后转换得到的数字表示。这里先理解转换结果，不展开分词算法。

原课按平均每个中文字约 1.5 个 Token 估算。这是平均值，并不存在半个 Token：具体字符可能对应一个、两个甚至三个 Token。

英文按平均每个单词约 1.3 个 Token 估算。不同单词的划分并不相同，词根、前缀等可能被分别划分。

因此，一段消息进入裸模型前，会先经过分词，转换成由多个 Token 组成的数字序列。

### 画面说明

便笺列出数字数组 [2,3,4,5,1,8]，并写有“中文：1个字≈1.5 token”“英文：1个单词≈1.3 token”。左侧输入标为 Token List。比例是本课使用的近似估算口径。

## 03. 输出是下一个 Token 的概率分布（02:05-03:23）

![场景 3](<keyframes/scene_003_00-03-15.jpg>)

### 完整内容

裸模型接收这串数字后，输出下一个 Token 的概率分布。

可以用对象表示这一结果：例如，下一个 Token 为 15 的概率是 0.7，即 70%；为 288 的概率是 0.2。模型会给出各候选 Token 的概率。

裸模型的核心工作是通过数学计算得到这一概率分布。日常 AI 工具的丰富功能，则由上层逻辑利用这一能力实现。

这些数字与自然语言之间存在对应关系，因此预测下一个 Token 也就能够逐步延续文本。例如，输入序列解码为“你好”，后续候选可能对应逗号，也可能对应“吗”。

### 画面说明

模型输出箭头标为“概率分布”。便笺展示 15:0.7、288:0.2 等候选项，旁边出现“你好”的续写示例；这些是教学示意，并非某个实际模型的实测概率。

## 04. 上下文窗口：长度与容量估算（03:23-05:31）

![场景 4](<keyframes/scene_004_00-05-01.jpg>)

### 完整内容

这个输入输出结构描述了裸模型的基本状态：根据已有内容预测后续 Token。

上下文窗口（Context Window）可以结合输入列表理解。本节用 Token 列表长度说明已使用的上下文，用模型允许的最大长度说明窗口容量。

例如，数组长度为 100，表示当前输入包含 100 个 Token。模型宣称的最大上下文窗口则表示可支持的最大长度。原课用截断示例说明超长输入：若上限为一万而输入两万，前面一万被丢弃；具体超限处理仍属于原课的简化说明。

原课以 128K 为常见示例。这里的 K 表示千，与磁盘空间无关；128K 对应约 12.8 万个 Token。

按每个中文字平均 1.5 个 Token 估算，128,000 ÷ 1.5 约为八万多个中文字符。其他示例还有 256K 和 1M；M 表示 million，即一百万，同样不是磁盘空间单位。

1M ÷ 1.5 约为六十六万个中文字符。这种换算用于估算窗口容量，实际数量取决于分词结果。

窗口能够容纳多少 Token，并不代表模型能同样有效地处理所有内容。原课提醒，应区分厂商公布的容量与实际使用效果。

### 画面说明

便笺依次列出“上下文窗口 / Context Window”、128K（12.8万 token）、256K 和 1M。讲解中的自动截断是原课描述，不能直接作为所有服务接口的行为保证；字符换算沿用本课的估算假设。

## 05. 装得下，不代表处理得好（05:31-06:50）

![场景 5](<keyframes/scene_005_00-06-31.jpg>)

### 完整内容

例如，某模型支持 1M 上下文，表示列表能容纳一百万个 Token，但填满窗口后，仍可能出现信息处理不充分的情况。

在较短对话中，模型可能能够遵循先前约定；随着对话变长，一些规则可能被遗漏。例如，忘记每次修改代码后提交，或忘记单个代码文件、模块不得超过 200 行的限制。

原课将这种现象归于长上下文下的能力下降。因此，处理相对独立的任务时，可以尽量使用新的上下文，减少无关信息的影响。

部分工具通过子代理处理独立任务，也是在应对这类上下文问题。

接下来分析模型内部参与运算的权重。前面用函数描述调用接口，而函数执行时还会使用权重矩阵。

### 画面说明

板书仍保持 Token List → Raw Model → 概率分布，以及上下文容量便笺；讲解由容量转向使用表现，再指回模型方框，为权重矩阵概念作过渡。

## 06. 权重矩阵、下载体积与参数量（06:50-08:28）

![场景 6](<keyframes/scene_006_00-07-52.jpg>)

### 完整内容

示意图中的函数与“权重矩阵”通过双向箭头连接，表示运算过程会读取模型权重。

本地部署模型时，下载的核心内容是权重矩阵，此外还会包含 config 等配置文件。

矩阵包含大量数字，是模型文件占用空间的主要来源。原课列举了几个 G、几十个 G、几百个 G，甚至一个 T 的下载体积示例。

参数量表示权重中数字的数量。B 是 billion，即十亿；7B 表示七十亿个参数，也就是七十亿个数字。

原课以 7B、16B 说明较小的本地模型，并以专用推理服务器上的商业模型说明更大的参数规模。讲者曾凭记忆提及 GPT-5 或其他模型超过 10T，但未确认具体模型与数据；此处仅保留单位解释：T 表示万亿，10T 为十万亿。

模型训练的目标是得到权重矩阵。具体训练方法、权重的形成过程及内部含义属于模型或算法工程的研究范围，本节只建立概念。

### 画面说明

Raw Model 与下方“权重矩阵”用双向箭头相连。便笺显示“模型参数”“7B”“70亿个参数”。“GPT-5还是其他模型超过10T”在原讲解中带有记忆不确定性，此处仅保留原话，不把该模型名称及规模当作已核实事实。

## 07. 训练、微调，以及语料为什么重要（08:28-09:16）

![场景 7](<keyframes/scene_007_00-09-11.jpg>)

### 完整内容

在本节的简化说明中，训练是从初始状态得到权重矩阵的过程。

微调则是在已有权重基础上进行二次训练，调整其中部分数值。这里从外部理解其作用，不展开内部训练方法。

训练与微调都需要语料。模型通过接触大量 Token 序列，学习根据已有输入预测下一个 Token 的概率分布。

编程模型可以利用开源库中大量不同编程语言的代码作为语料，从而学习代码中的 Token 关系并进行后续预测。

### 画面说明

指向权重矩阵的左侧箭头标有“训练/微调”，下面标有“语料”，直观区分训练材料、形成的权重与运行时的 Token 输入。

## 08. 通过模型架构调用权重（09:16-10:07）

![场景 8](<keyframes/scene_008_00-10-02.jpg>)

### 完整内容

训练得到的权重需要结合相应计算方式才能使用。原课以 Hugging Face 相关库为例，说明如何通过程序调用模型。

调用方式与模型架构有关。原课以 Transformer 为主要例子，通过与该架构对应的函数读取权重并执行运算。

不同架构使用权重的方式可能不同。原课还提到 Tensor〔术语保留原稿，具体所指见校读说明〕；核心意思是调用方式应与训练时采用的架构相匹配。

例如，基于 Transformer 训练的权重通常由相应架构调用。若尝试通过其他架构使用，原课指出可能涉及权重转换。

### 画面说明

便笺上写有“Transformer架构”和“Tensor架构”。这里忠实保留原课的术语及说法；Tensor 的具体所指没有展开，不把它补写成经核实的另一种模型架构。

## 09. 输入、权重与算法共同产生输出（10:07-11:00）

![场景 9](<keyframes/scene_009_00-10-40.jpg>)

### 完整内容

这里讨论的是神经网络和深度学习中的调用模式，其他机器学习方法未必采用同样的结构。

整体过程是：将 Token 列表传给基于 Transformer 架构的函数，函数结合输入、权重矩阵中的参数及算法进行计算，得到下一个 Token 的概率分布。

从本节采用的数学抽象看，模型调用可以视为纯函数：在输入及运算条件固定时，输出由输入决定。

### 画面说明

图中以红框标出 Token List、Raw Model 和权重矩阵，展示输入、计算过程与参数的关系。此处“纯函数”是原课采用的数学抽象，下一段继续补充实际计算误差。

## 10. 数学函数、GPU 与浮点数误差（11:00-12:59）

![场景 10](<keyframes/scene_010_00-12-31.jpg>)

### 完整内容

可以用简单函数作类比：输入 1、2、3 得到某个固定结果，或计算 1 + 2 = 3。模型的运算公式复杂得多，但同样是在执行数学计算。

因此，本节从技术计算过程解释模型行为，避免将回复中的情绪表达直接当作模型产生情感或自我意识的证据。

实际运行还涉及数值计算。参数量大、运算多时，GPU 会将任务拆分并行计算，再合并结果。

计算机浮点数运算可能不满足结合律。原课通过控制台比较 0.1 + 0.2 + 0.3 与 0.1 + (0.2 + 0.3)，展示两种运算顺序可能产生不同的误差表现。

因此，数学上等价的运算顺序，在浮点数实现中不一定得到完全相同的结果。

长公式被拆分时，拆分和合并顺序的差异可能影响最终数值。这解释了理论上的纯函数抽象与实际 GPU 运算表现之间的差别。

多模态也可以沿用输入、运算与输出的分析方式。

### 画面说明

浏览器控制台完整显示：0.1+0.2+0.3 → 0.6000000000000001；0.1+(0.2+0.3) → 0.6；两式比较得到 false。这是浮点加法顺序的演示。“感情、自我意识”等评论属于原讲者观点，不能把函数示意视为对该议题的完整证明。

## 11. 多模态：数字输入与输出解释（12:59-14:44）

![场景 11](<keyframes/scene_011_00-14-34.jpg>)

### 完整内容

模型接收的是数字表示，并通过运算预测后续 Token 的概率。

图片、视频、音频和文字都需要转换为模型能够处理的数字表示，因此可以从统一的输入输出角度理解多模态。

不同模态还涉及各自的内部实现。本节不展开这些细节，只强调训练内容与模型能够处理的任务之间的联系。

模型输出后，还需要根据其含义进行解释。例如，用户要求生成图片，得到下一个 Token 的概率分布并选择 Token 后，需要识别其表示的是文本还是图像信息。

原课用词表区间作简化示例：假设 Token 500008 落在 image 区间，就按图像相关信息进行后续转换，得到图像中的相应信息，例如某个像素点。这里的数字与解码过程均为示意。

### 画面说明

板书保留 Token List、Raw Model、GPU、权重矩阵及概率分布。便笺标注“多模态 没有区别”，并写出 500008 指向 image_file 的例子。该编号和像素解释是原课的简化示意，不是具体多模态系统的通用编码规范。

## 12. 回到整体结构，衔接模型服务（14:44-15:36）

![场景 12](<keyframes/scene_012_00-15-30.jpg>)

### 完整内容

原课认为，自 Transformer 出现至录制时，其核心输入输出框架保持了较高稳定性。

变化主要涉及权重的训练、语料的类型与模型能力。例如中文、英文、代码和图像语料用于适配不同 Token 的预测，不同模型也有不同的权重与上下文上限。

这里所说的“基础能力没有本质变化”，指的是根据输入调用权重、计算下一 Token 概率分布这一抽象。

理解这一层后，可以继续分析模型服务如何在裸模型基础上组织调用并提供更完整的能力。
